# ZELO 2.0 — Code Challenge Evaluation & Test Case Specification

**File:** `CODE_CHALLENGE_EVALUATION_SPEC.md`
**Version:** 3.7
**Status:** Draft — Pending Approval
**Product:** ZELO — Learn. Practice. Build.

---

## 1. Purpose

This document defines how ZELO evaluates coding challenge submissions.

It covers:

* Challenge definitions and starter code.
* Supported programming environments.
* Visible and hidden test cases.
* Run and Submit operations.
* Compilation and runtime errors.
* Output comparison.
* Time and resource limits.
* Feedback presentation.
* Reward eligibility.
* Evaluation security and reliability.

The goal is to provide beginners with accurate, actionable feedback without exposing hidden tests or compromising the platform.

## 2. Core Principles

1. **Correctness first:** Evaluation results must reflect the challenge's actual requirements.
2. **Useful feedback:** Learners should understand what failed whenever safe and practical.
3. **Safe execution:** Untrusted code must never execute inside the trusted application server process.
4. **Separate Run and Submit:** Running code for exploration is different from submitting it for evaluation.
5. **Fair testing:** Tests must cover meaningful behaviour rather than depend unnecessarily on implementation details.
6. **No false success:** A successful compilation does not mean a challenge has passed.
7. **No hidden-test leakage:** Private evaluation data must remain on the trusted side.
8. **Learning over punishment:** Failed submissions should help learners improve.

## 4. Challenge Definition

Every published coding challenge must have a stable definition.

### Required metadata

* Challenge ID.
* Title and instructions.
* World, module, and lesson association.
* Language and runtime.
* Difficulty classification.
* Starter code.
* Expected behaviour.
* Evaluation strategy.
* Test definitions or test-suite reference.
* Resource limits.
* Completion criteria.
* Publication status and version.

### Example conceptual definition

```json
{
  "id": "js-functions-001",
  "title": "Create a Greeting Function",
  "language": "javascript",
  "instructions": "Write a function that returns a greeting.",
  "starterCode": "function greet(name) {\n  // Write your solution\n}",
  "evaluationMode": "function-tests",
  "completionRule": "all-required-tests-pass"
}
```

This is an illustrative content example, not a final API or storage schema.

The challenge definition must also specify the function signature or interface that the learner is expected to implement.

## 5. Supported Evaluation Modes

Different types of coding exercises require different evaluation methods.

| Mode                   | Suitable use                                     | Evaluation                                                                   |
| ---------------------- | ------------------------------------------------ | ---------------------------------------------------------------------------- |
| Output comparison      | Introductory exercises with deterministic output | Compare actual and expected output under defined rules.                      |
| Function tests         | JavaScript function challenges                   | Invoke the expected function with defined inputs and compare results.        |
| HTML preview           | HTML fundamentals                                | Render the document in a restricted preview environment.                     |
| HTML/CSS visual checks | Styling and layout exercises                     | Validate supported structural or computed-style requirements.                |
| React component checks | Component-building exercises                     | Render within an approved constrained runtime and test observable behaviour. |

Not every mode must be implemented in the first release.

### Initial implementation principle

Start with the smallest set of evaluation modes that supports the first published coding lessons. Add more advanced visual and component evaluation only after its correctness and security requirements have been validated.

## 6. Run vs Submit

These operations serve different purposes.

### Run

Run allows learners to experiment with their current code.

Expected behaviour:

* Execute or preview the current code using the approved environment.
* Display output or a preview.
* Display syntax and runtime errors.
* Avoid granting completion XP merely for running code.
* Apply resource limits and execution quotas.
* Avoid marking the challenge complete solely because the code ran successfully.

### Submit

Submit requests formal evaluation against the challenge's required criteria.

Expected behaviour:

1. Validate the submission and challenge access.
2. Evaluate against the appropriate test suite.
3. Return a normalized result.
4. Determine whether the challenge's completion criteria are satisfied.
5. Persist the authoritative result when required.
6. Update progress and reward eligibility through the approved server workflow.

A learner may run code several times before submitting it.

## 7. Test Case Types

### A. Visible tests

Visible tests may show:

* The example input.
* The expected output.
* The actual output.
* Whether the test passed.

They help learners understand the required behaviour.

### B. Hidden tests

Hidden tests verify additional cases that should not be disclosed.

They may cover:

* Boundary values.
* Empty inputs.
* Different valid inputs.
* Unexpected but permitted inputs.
* Correct handling of edge cases.

The client must not receive hidden input values, expected outputs, private assertions, or the hidden test source.

### C. Test-suite integrity

Each test suite must be reviewed to ensure:

* Tests match the written instructions.
* Expected results are correct.
* Tests do not contradict one another.
* Edge cases are relevant to the learning objective.
* Tests do not rely unnecessarily on formatting or internal implementation choices.

Hidden tests must not be used to enforce undocumented requirements.

## 8. Evaluation Result Model

The evaluator should return a normalized result rather than exposing raw internal runtime details.

| Status           | Meaning                                                       |
| ---------------- | ------------------------------------------------------------- |
| `QUEUED`         | Evaluation has been accepted but has not started.             |
| `RUNNING`        | Evaluation is in progress.                                    |
| `PASSED`         | All required tests passed.                                    |
| `FAILED`         | At least one required correctness test failed.                |
| `COMPILE_ERROR`  | Code could not be compiled or parsed in the selected runtime. |
| `RUNTIME_ERROR`  | Code failed during execution.                                 |
| `TIMEOUT`        | Execution exceeded the permitted time.                        |
| `RESOURCE_LIMIT` | Execution exceeded an approved resource limit.                |
| `SYSTEM_ERROR`   | The evaluation infrastructure failed.                         |
| `CANCELLED`      | The operation was cancelled under an approved policy.         |

Not every language or evaluation mode needs every status.

A system failure must not be represented as a learner correctness failure.

## 9. Output Comparison Rules

Output comparison must be explicitly configured for each challenge.

Possible policies include:

* Exact string comparison.
* Comparison after defined newline normalization.
* Structured-value comparison.
* Numeric comparison with a documented tolerance.
* Function return-value comparison.

Do not globally trim whitespace or ignore differences without considering the challenge requirements.

For example:

* A challenge about exact formatting may require whitespace-sensitive comparison.
* A function returning a number should normally be compared numerically.
* A JSON-like result should be compared structurally when ordering and representation are not part of the objective.

The expected result and comparison policy must be reviewed before publication.

## 10. Error Feedback

The learner should receive a useful explanation of what happened.

### Syntax or compilation error

Show a safe error message and relevant location information where available.

### Incorrect result

Show the relevant visible test, expected result, and actual result when safe and appropriate.

### Runtime error

Explain that the program failed during execution. Provide a sanitized message and useful location information where supported.

### Timeout

Explain that the program did not finish within the allowed time.

### Resource limit

Explain that execution exceeded the permitted resources, without revealing infrastructure internals.

### System error

Explain that ZELO could not complete the evaluation. Preserve the learner's code where possible and allow a safe retry.

### Hidden-test failure

The result may indicate that additional cases failed without revealing hidden inputs or expected outputs.

Feedback must not expose environment variables, secret paths, internal credentials, infrastructure configuration, or private test code.

## 11. Pass/Fail Rules

A challenge passes only when its required evaluation conditions are satisfied.

The default proposed rule is:

**All required tests must pass.**

A challenge may use another explicit scoring rule only when the lesson specification defines it and the learner-facing instructions explain the relevant requirements.

### Required distinctions

* Successful execution is not equivalent to correctness.
* Passing visible tests is not sufficient when hidden tests are required.
* A partial score must not mark a challenge complete unless the approved completion rule permits it.
* A system error must not count as a failed learner submission.
* The same successful challenge must not repeatedly generate completion rewards.

The authoritative pass result must be calculated by the evaluator or trusted backend, never by the client.

## 12. Resource Limits and Execution Security

All execution limits must be configured and tested for the selected runtime.

Controls should include:

* Execution timeout.
* Memory limit.
* CPU or equivalent resource limits.
* Maximum submission size.
* Maximum output size.
* Concurrency limits.
* Request quotas.
* Restricted filesystem access.
* Network access disabled by default.
* No access to production secrets or databases.
* No arbitrary package installation.
* Safe cancellation and cleanup.

### Isolation requirements

Untrusted code must run inside a suitable sandbox or isolated execution service.

A browser preview is not automatically a complete security boundary. HTML, CSS, JavaScript, and React previews must be designed to prevent untrusted code from accessing privileged application context.

Server-side execution must not run directly in the main API process.

The chosen implementation must undergo a security review before accepting arbitrary learner code.

## 13. Timeouts and Asynchronous Evaluation

Some challenges may finish quickly; others may require a background evaluation job.

The system must define which evaluation modes run synchronously and which use asynchronous jobs.

For asynchronous evaluation:

* Assign a stable evaluation identifier.
* Return `QUEUED` or `RUNNING` as appropriate.
* Allow the client to retrieve the current status.
* Stop waiting after the defined timeout.
* Clean up abandoned jobs.
* Prevent duplicate reward issuance if a result is retrieved repeatedly.
* Handle worker failures without corrupting learner progress.

The client should not repeatedly create new jobs simply because a status request was delayed.

## 14. Persistence and Reward Integration

Persisted records may include:

* Challenge ID and version.
* User ID.
* Submission reference.
* Evaluation status.
* Test counts or approved result summaries.
* Completion result.
* Creation and completion timestamps.

Store only the code and result information needed for learning functionality, debugging, and the approved retention policy.

### Reward rules

* Run operations do not award challenge-completion XP.
* Failed submissions do not award completion XP.
* First eligible successful completion may award the configured reward.
* Repeated successful submissions do not award the same one-time reward again.
* A timed-out or system-failed evaluation must not create a false pass result.
* A retry after a system failure must not be counted as a new reward event.

Submission history retention and privacy rules remain subject to the approved data policy.

## 15. Testing Strategy

### Unit tests

Test:

* Output comparison rules.
* Evaluation result normalization.
* Pass/fail determination.
* Challenge eligibility.
* Reward idempotency.

### Integration tests

Test:

* API validation and authorization.
* Evaluator request and response contracts.
* Hidden-test isolation.
* Persistence of evaluation results.
* Timeout and system-error handling.
* Retry behaviour.

### End-to-end tests

Test the learner journey:

1. Open a published coding challenge.
2. Edit the starter code.
3. Run the code.
4. Inspect output or errors.
5. Submit the solution.
6. Receive evaluation feedback.
7. Correct an error and retry.
8. Complete the challenge.
9. Verify progress and reward behaviour.

### Security tests

Test:

* Attempted filesystem access.
* Attempted network access.
* Excessive execution time.
* Excessive memory and output use.
* Malicious HTML or JavaScript in previews.
* Access to another user's submission.
* Attempts to access hidden tests.
* Duplicate submission and reward requests.

## 16. Acceptance Criteria

The evaluation system is ready for MVP release when:

* [ ] Published challenges have valid evaluation definitions.
* [ ] Run and Submit behave as separate operations.
* [ ] Required visible tests work correctly.
* [ ] Hidden tests remain private.
* [ ] Incorrect outputs produce accurate failure results.
* [ ] Syntax, runtime, timeout, and system errors are distinguishable.
* [ ] Output comparison follows a documented policy.
* [ ] Execution limits are enforced.
* [ ] Untrusted code runs within an approved isolation boundary.
* [ ] The client cannot manufacture a passing result.
* [ ] System errors do not incorrectly punish the learner.
* [ ] Successful challenge rewards cannot be duplicated.
* [ ] Evaluation failures have safe recovery paths.
* [ ] The implemented execution environment passes security tests.

## 17. Open Decisions

Resolve these before implementing the relevant evaluation mode:

1. Which languages and runtimes are supported in the first release?
2. Which execution modes are included in the initial MVP?
3. Which sandbox or isolated execution service will be used?
4. What are the resource limits for each runtime?
5. Which test framework or evaluation protocol will be used?
6. How will React and visual HTML/CSS challenges be evaluated?
7. Which test details may be shown to learners?
8. How long will submissions and evaluation results be retained?
9. Which evaluations run synchronously versus asynchronously?
10. How will evaluator infrastructure failures be retried safely?

---

## 18. Final Rule

**A coding challenge is complete only when its approved evaluation criteria are satisfied by a trusted evaluator.**

ZELO must distinguish between running code, producing output, passing tests, and earning completion rewards.

The evaluation system should make debugging understandable for beginners while keeping execution secure, feedback accurate, and progress reliable.
